# Content sources

The app bundles one read-only SQLite content database, `assets/content/content.db`, covering the whole Quran. It is generated by the content build from third-party sources, which are kept out of git in `content/sources/`.

```sh
npm run content:fetch   # downloads the sources and the KFGQPC font (checksum-verified)
npm run content:build   # writes assets/content/content.db
```

Bump `CONTENT_VERSION` in `src/content/version.ts` whenever the generated database changes, so installed apps pick up the new copy.

## Content updates

Installed apps can get a newer content database (data fixes, a new QuranEnc version) without a store release. The app reads a manifest from `CONTENT_MANIFEST_URL` (`src/content/update/config.ts`), the `content-manifest.json` asset of the fixed `content-latest` GitHub release:

```json
{
  "version": 5,
  "schema": 1,
  "url": "https://github.com/Krsho/Lisan/releases/download/content-v5/content-v5.db",
  "sha256": "<lowercase hex sha256 of the file>",
  "bytes": 13901824
}
```

- `version` is the database's `meta.content_version` (`CONTENT_VERSION`). The app downloads it only if it is newer than the database it has open.
- `schema` is `CONTENT_SCHEMA` (`src/content/version.ts`): the table layout. Bump it when tables or columns change in a way older app builds cannot read. An app only downloads a database of its own schema, so a new schema reaches users through an app update.
- At most once a day, in the background, the app downloads the file to `content-vN.db.part`, checks its sha256, opens it (`PRAGMA integrity_check`, `content_version`), renames it to `content-vN.db`, and only then records it as active in `content-update.json` (app documents; never the user database). The new database opens on the next app start. If any step fails, the old database stays in use. A newer bundled database (from an app update) wins over an older download.
- Learner progress lives in the user database and refers to content by stable references (`surah:ayah:word`, lemma text, glossary term keys), so it survives an update. Keep these stable between content versions. Do not use `terms.id` outside the content database: it is numbered by the order of `content/glossary.json`.

### Releasing a content update (human step)

Before the first public release, check the licenses in [Sources](#sources): posting the database is redistribution, the same as shipping it in the app (KFGQPC and Tarteel permission; no Quran Foundation content in it).

1. Bump `CONTENT_VERSION`, run `npm run content:build`, run `npm run check`, and merge the change (the bundled database and the release must have the same content for the same version).
2. `npm run content:release`. It checks the database and writes `dist/content-release/content-vN.db` and `content-manifest.json`, then prints the commands for the next two steps.
3. Upload the database to its own release: `gh release create content-vN dist/content-release/content-vN.db --title "Content vN" --notes "<what changed>"`.
4. Replace the manifest on the `content-latest` release: `gh release upload content-latest dist/content-release/content-manifest.json --clobber`. The first time, create that release instead: `gh release create content-latest dist/content-release/content-manifest.json --title "Latest content" --notes "Manifest read by the app" --latest=false`.
5. Check: `curl -L https://github.com/Krsho/Lisan/releases/download/content-latest/content-manifest.json` shows the new version, and an installed app shows it under "About and sources" after two starts (one to download, one to open it).

Upload the database before the manifest, so the manifest never points to a missing file. To withdraw a bad release, upload the previous manifest again; apps that already switched keep the bad version until a higher one is published, so fix forward with a new version.

## How the Quran text is used

- The text is shown as KFGQPC writes it. The build only removes what is not part of a word: the ayah-end glyph at the end of each ayah (the app draws ayah numbers itself) and the ۞ rubʿ al-ḥizb mark (kept as a flag on the ayah).
- Pause marks (ۖ ۗ ۚ ۛ ۘ ۩) stay attached to the word they follow. Each word also has a `bare` form without them, for quiz and review cards.
- The Basmala is ayah 1:1 only. Surahs 2–114 except 9 show it as a header (`surahs.has_basmala`), reusing the words of 1:1; it is not an ayah there.
- Words are split on spaces and must line up with the corpus morphology. In seven ayahs KFGQPC's word boundaries differ from the corpus's (`بَعۡدَ مَا` in 2:181, 8:6, 13:37; `إِلۡ يَاسِينَ` in 37:130; `لَّوۡمَا` 15:7, `مَالِيَ` 27:20, `وَمَالِيَ` 36:22). These are listed in `tools/content-build/alignment.ts`: one displayed word covers whole text tokens and whole corpus words, and the text is never re-split. The build refuses any other mismatch.
- QUL's word-by-word glosses use their own word numbering, which the same table maps onto the displayed words.
- Lemma frequencies (how many corpus segments have each lemma) are counted over the whole Quran into the `lemmas` table.

## Translation and tafsir

Both are stored and shown exactly as QuranEnc publishes them, keyed by language (`ayah_texts` and `editions` tables). Two consequences:

- Rowwad's translator footnotes are kept: `[n]` markers stay in the translation and the `[n] note` entries are shown below it. (QuranEnc's SQLite has an empty string where the API has `null`; both are stored as `NULL`.)
- Every Mukhtasar entry starts with its ayah number, e.g. `"2. All praise belongs…"`. This prefix is **kept, not stripped**: it is part of QuranEnc's text, and it carries information. Where the Mukhtasar explains several ayahs together it reads `"12-13. …"` on each of them, and it exposes source errors: 86 ayahs carry a number other than their own. Most are grouped or repeated verses (26:68 reuses the note for the identical 26:104), but some look wrong, e.g. 2:3 holds the text for 2:4. Report these to QuranEnc (their terms ask for notes on the translation) rather than fixing them here.

The attribution screen reads each edition's title, link and version from the database.

## Glossary

`content/glossary.json` is authored for Lisan (not third-party): every grammatical term the word details use, keyed by a stable term id, with its Arabic name and, per explanation language, a name and short definition. The content build maps each corpus morphology tag to a term and refuses to build if a tag is unknown or a term has no entry. To add a language, add its key (e.g. `"bs"`) to each term; missing translations fall back to English.

## Fonts

Quran text is rendered with **KFGQPC Uthmanic Script Hafs v9** (`assets/fonts/UthmanicHafs-v9.otf`). Its license forbids reproduction without the written approval of the King Fahd Glorious Quran Printing Complex, so the file is **not committed**: `npm run content:fetch` downloads a checksum-verified copy (the official download is no longer available; the source is a pinned commit of the [quranwbw/qpc-fonts](https://github.com/quranwbw/qpc-fonts) mirror). Commit it only once KFGQPC grants permission. If permission is refused, fall back to Amiri Quran (SIL OFL).

The font is configured only in `src/theme/quranFont.ts`.

KFGQPC fonts are designed for KFGQPC's own encoding of the text, which is why the displayed text is KFGQPC's (with Tanzil's text, the small high rounded zero U+06DF showed as a dotted circle). Every code point of the v2.0 text is in the v9 font, but the rendering of the whole text still has to be checked on a device. If v9 misrenders it, switch to the v20 font (`uthmanic_hafs_v20.ttf`, in the same KFGQPC zip and under the same terms).
